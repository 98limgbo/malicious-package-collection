## 배경 / 목적
- 악성 패키지 탐지 연구의 타당성 검증을 위해 npm, PyPI, RubyGems 외 다양한 레지스트리(crates.io, Packagist, Go, Maven, NuGet, Hex, Pub)에서 악성 패키지 **원본 파일**을 수집한다.
- 데이터 소스: [ossf/malicious-packages](https://github.com/ossf/malicious-packages) (GitHub, 원본) / [OSV.dev](https://osv.dev) (재검증용 API)
- 핵심 제약: 악성 패키지는 보고된 후 원본 레지스트리에서 빠르게(수시간~수일 내) 삭제되는 경향이 있어, 최대한 빠르게 감지하고 다운로드해야 한다.

## 전체 구조 요약

- **수집(`collect.py`)**: 새로운 악성 패키지 리포트가 보고됐는지 감지하고, 발견되면 즉시 다운로드 시도. GitHub diff로 5분 주기 자동 반복 실행한다.
- **재검증(`verify.py`)**: 이미 수집한 리포트가 철회되지 않았는지, 수집한 버전이 최신 리포트의 버전 목록과 여전히 일치하는지 OSV API로 확인. 자동 스케줄 없이 필요할 때 수동 실행한다.

## 저장 원칙
- `data/<registry>/<MAL-ID>/` 구조로 저장한다. 한 리포트가 여러 생태계·여러 버전의
  패키지를 포함할 수 있기 때문에, MAL-ID 단위 폴더로 나눠야 재수집 시 어떤 파일이
  어느 리포트에 속하는지 구분되고 덮어쓰기 기준도 명확해진다.
- 다운로드한 원본 파일(tarball/zip/jar 등)은 압축을 풀지 않고 그대로 저장한다.
  압축을 풀면 그 안의 실행 파일이 노출되어 실수로 실행될 위험이 커지기 때문이다.
- **OSV/레지스트리 원본값**(`osv_*`, `registry_published_at`, `earliest_registry_published_at`)은
  원본 그대로 보존한다 (마이크로초 등 원본 정밀도를 임의로 깎으면 원본과 비교/재검증 시 어긋날 수 있다).
- **우리 파이프라인이 직접 생성하는 값**(`collected_at`, `download_attempted_at`, `downloaded_at`,
  `osv_last_checked_at`)은 초 단위로 단순화한다 (5분 주기 파이프라인에서 마이크로초 단위 구분은
  분석 가치가 없다).

## 보존 정책

### 철회된 리포트는 다운로드하지 않는다
`withdrawn` 값이 있는 리포트는 OSV가 오탐으로 인정한 것이므로 악성이라는 근거가 없다. 그래서 `mal_reports`에 기록만 남기고 `collected_artifacts`는 만들지 않으며 파일도 받지 않는다. 수집한 뒤에 리포트가 철회되면 갱신을 감지한 시점에 기존 파일과 폴더도 삭제한다. 이 덕분에 분석 전에 철회 여부를 따로 검증하지 않아도 된다.

처음에는 오탐 사례도 연구 자료가 될 수 있다는 이유로 철회된 리포트도 받았다. 그런데 실제로 운영해보니 철회 리포트 파일이 전체의 3.32%였고, 하나의 리포트가 1,683개 버전을 차지하기도 했다. 이 데이터가 악성 샘플 사이에 섞이면 위악성이 되므로 정책을 바꿨다. 철회 사실 자체는 `osv_withdrawn_at`에 남는다. 위악성 사례는 [`data_quality_notes.md`](data_quality_notes.md)를 참고한다.

### 실패한 버전은 남기지 않는다
목적이 "악성 패키지 **파일** 수집"이지 시도 기록 자체가 아니므로, 실패한
`collected_artifacts` 행은 즉시 삭제한다. "언제 시도했는지"는
`mal_reports.download_attempted_at` 하나로 충분히 추적 가능하다 (버전별로 남길
필요는 없다).

### 파일을 하나도 못 구한 리포트도 SQL 행은 유지한다
`report.json`/폴더는 삭제하되(연구 대상이 아니므로), `mal_reports` SQL 행은
유지한다. 이유:
1. `report.json` 내용은 GitHub/OSV에 원본이 남아있어 `mal_id`만 기억하면 나중에
   다시 조회할 수 있다.
2. GitHub diff 기반 감지는 체크포인트가 앞으로만 이동하므로 정상 운영 중엔 같은
   리포트를 재감지할 일이 없지만, 수동으로 과거 구간을 재스캔할 경우 SQL 기록이
   없으면 이미 실패한 걸 다시 시도하는 헛수고가 발생한다.

## 수집 (`collect.py`)

### 감지 신호: GitHub 우선, OSV는 재검증 전용
OSV.dev의 importer는 GitHub 등 소스를 15분 주기로만 폴링해 반영하는 구조적 지연이 있다. `ossf/malicious-packages`(GitHub)가 원본(canonical)이므로 감지는 GitHub에서 직접 한다 (OSV.dev API는 재검증 전용).

### 첫 실행: 벌크 zip 백필
`sync_state`에 체크포인트가 없으면(첫 실행) 그해(`MAL-<연도>-*`) 리포트 전체를 백필한다.
- **방식**: 지원하는 10개 레지스트리 각각의 OSV 벌크 zip(`gs://osv-vulnerabilities/<생태계>/all.zip`)을 다운로드해 로컬에서 `MAL-<연도>-*.json`만 필터링.
- **왜 zip인가**: GitHub 트리 API는 대량 조회 시 응답이 잘릴(truncated) 수 있고, OSV 리포트를 개별 파일로 하나씩 요청하는 것도 왕복 지연시간 때문에 매우 느림 (실측: 292건 개별 조회는 1시간 넘게 걸림 vs zip 10개 생태계 전체는 2분 미만). `modified_id.csv` 색인을 거쳐 개별 조회하는 방식도 시도했으나 같은 이유로 zip으로 교체함.
- 백필이 끝나면 그 시점 GitHub HEAD 커밋을 체크포인트로 저장하고, 이후부터는 diff 모드로 전환. 다른 연도를 나중에 채우고 싶으면 `scripts/backfill_year.py`(README 참고)로 별도 실행.

### 정상 운영: GitHub diff (5분 주기)
`GET /compare/{last_sha}...{head_sha}`로 `osv/malicious/` 아래 변경 파일만 조회. 가볍고 빠름.

**잘림 방지**: 변경 파일이 250개 이상이면(GitHub API가 300개 근처에서 응답을 자를 수 있음) diff 결과를 신뢰하지 않고 자동으로 벌크 zip 백필로 대체한다 (PC가 오래 꺼져있던 경우 등 대비). 이미 처리된 리포트는 `osv_modified_at` 비교로 스킵되므로 안전하게 재실행 가능.

### 버전 결정 로직
리포트의 `affected[]` 항목마다:
1. **명시적 버전 목록**(`versions`)이 있으면 그대로 사용한다. 이때 `collected_artifacts.is_explicit_version`은 1이다.
2. 없고 범위(`ranges`)에 **상한**(`fixed`/`last_affected`)이 있으면 → 일부 버전만 악성이라는 뜻이므로 **스킵**한다. 전체 버전을 받으면 정상 버전을 잘못 수집할 위험이 있다. 실측 기준 이런 케이스는 전체 리포트의 0.00%(5건)뿐이다.
3. 없고 범위에 상한이 없으면("전 버전이 악성") → 레지스트리에서 게시된 버전과 게시일을 함께 조회하되, **리포트 등록일(`osv_published_at`) 이후에 게시됐거나 게시일을 알 수 없는 버전은 제외**하고 나머지를 다운로드한다. 이때 `is_explicit_version`은 0이다. 전체 리포트의 89.31%가 이 유형이다.

#### 왜 등록일 이후 버전을 제외하는가
리포트를 작성한 쪽은 작성 시점에 존재하지 않던 버전을 검토할 수 없다. 그런데 전체조회는 수집 시점의 현재 버전을 모두 나열하기 때문에, 등록 이후에 나온 버전(예: 활발히 운영되는 정상 프로젝트의 이후 릴리스)까지 악성으로 수집한다. 게시일을 알 수 없는 버전은 등록일 이전인지 확인할 수 없으므로 보수적으로 제외한다.

#### 왜 버전 명시 리포트에는 적용하지 않는가
명시 리포트는 시간이 지나면서 악성 버전이 목록에 추가된다. 그래서 등록일 이후에 게시된 버전이 목록에 있는 것이 정상이고, 실제로 명시 방식 파일의 약 28%가 등록일 이후에 게시된 버전이다. OSV가 그 버전을 직접 확인해서 못박은 것이므로 날짜로 걸러내면 오히려 확실한 악성 데이터를 잃는다.

#### 왜 갱신일(`osv_modified_at`)이 아니라 등록일을 기준으로 하는가
갱신일은 "악성임을 다시 확인한 날"이라고 볼 수 없다.
- OSV의 일괄 작업이 여러 리포트의 갱신일을 같은 초로 한꺼번에 바꾸는 사례가 있었다.
- 철회처럼 악성이 아니라고 정정하는 경우에도 갱신일이 바뀐다.

철회 리포트를 제외한 뒤 두 기준의 실제 차이는 35건뿐이었다(등록일 기준 122건, 갱신일 기준 87건 제외). 손실이 작으므로 더 보수적인 등록일을 택했다.

#### 버전 하나뿐인 패키지는 신뢰도가 높다
전체조회 패키지 중 버전이 하나뿐인 경우가 약 6만 1천 개이고, 그중 99.98%가 등록일 이전에 게시되었다. 버전이 하나뿐이면 어느 버전이 악성인지의 모호함이 없다.

### 다운로드: 원본만, 미러 없음
`registries/*.py`가 레지스트리별 원본 다운로드 + `list_versions_with_dates()`(위 3번 케이스용)를 구현한다. npm과 PyPI는 응답 한 번에 버전과 게시일을 함께 받아서 추가 호출이 없다. 나머지 레지스트리는 기본 구현이 버전별로 게시일을 조회하는데, 컷오프가 의미 있는 곳이 사실상 npm(전체조회 항목의 96.87%)과 PyPI(3.1%)뿐이라 그대로 두었다. RubyGems와 NuGet은 전부 버전 명시 리포트라서 컷오프의 영향을 받지 않는다.

**npm 보안 홀딩 더미는 수집하지 않는다.** npm은 악성 패키지를 제거한 뒤 같은 이름에 `description: "security holding package"`, `repository: "npm/security-holder"`가 들어 있는 빈 플레이스홀더를 올려둔다. 오래된 리포트를 전체조회하면 원본은 이미 지워지고 이 더미만 남아서, 실제로 npm 성공 다운로드의 약 63%가 더미였다. 다운로드한 패키지의 `package.json`에서 이 마커를 발견하면 수집 실패로 처리하며, 더미의 게시일은 악성 코드의 게시일이 아니므로 게시일 조회도 하지 않는다.

**미러 폴백은 없음** — jsDelivr(npm), Software Heritage(범용) 둘 다 검증해봤으나 필요한 시점에 콘텐츠가 없거나(SWH는 크롤링 주기가 삭제 속도를 못 따라감) 악성 코드가 이미 제거된 상태(jsDelivr, 12건 전수조사 100% 무해 파일만 남음)라 무의미했음.

### 다운로드 완료 판정 (즉시 처리)
`download_pending()`이 파일 하나를 처리할 때마다 그 자리에서 바로 확인: 그 리포트에 남은 `pending`이 없으면 즉시 `download_attempted_at` 기록 + 성공 0건이면 폴더 삭제. (전체 배치가 끝난 뒤 한꺼번에 처리하면 "처리 시각"이 부정확해지므로 인라인으로 처리) 실행이 중간에 끊겨 인라인 처리를 못 받은 리포트는 다음 실행 끝의 안전망(`finalize_reports`)이 훑어서 정리.

## 재검증 (`verify.py`, on-demand)

**대상**: `success_count > 0`인 리포트만 (파일 없는 리포트는 검증할 대상이 없음).

각 대상마다:
1. OSV API로 최신 리포트 조회, `osv_last_checked_at`은 결과와 무관하게 항상 갱신
2. `mal_reports.osv_modified_at`과 비교해 변경 없으면 종료
3. 변경 있으면 `report.json` 갱신 + `mal_reports.osv_modified_at`/`osv_withdrawn_at` 갱신
4. 철회 상태면 → 이 mal_id의 `collected_artifacts` 전 행을 `osv_verification_status='withdrawn'`. 다만 정상 운영에서는 수집 단계가 철회를 감지하는 즉시 파일을 삭제하므로, 이 분기는 감지가 누락된 경우의 안전망이다.
5. 철회 아니면 → 성공한 각 버전이 최신 리포트의 버전 목록에도 있는지 확인 → 없으면 `mismatch`, 있으면 NULL로 리셋 (재검증마다 처음부터 다시 판정하므로 상태 복구도 자동으로 됨)

## 검토 라벨 (`review_label`)

수집한 파일이 실제로 악성인지를 사람이 확인한 결과를 `collected_artifacts.review_label`에 기록한다. 값은 `NULL`(미검토), `confirmed_malicious`, `false_positive`(위악성), `research_poc`(동작은 악성이지만 의도는 승인된 연구) 네 가지이다.

- **수집 루프는 이 컬럼을 판단하지 않는다.** 위악성은 자동으로 가려낼 수 없어서 사람이 가끔 확인한 결과만 넣는다. 이미 있는 행은 `INSERT OR IGNORE`로 덮어쓰지 않으므로, 리포트가 갱신되어도 라벨이 유지된다.
- **판단 단위는 리포트가 아니라 파일(패키지-버전)이다.** 한 리포트 안에 진짜 악성 버전과 오탐 버전이 섞일 수 있기 때문이다(`MAL-2026-5186`은 Google이 웜으로 지목한 버전과 Inspector가 휴리스틱으로 지목한 정상 버전이 한 리포트에 병합되어 있다).
- **`research_poc`를 `false_positive`와 따로 둔다.** 연구용 PoC는 설치 시 외부 전송이라는 실제 동작이 있어서 오탐이 아니다. 라벨을 동작 기준으로 둘지 의도 기준으로 둘지는 사용하는 쪽이 고를 수 있어야 한다.
- **판단 근거는 DB가 아니라 [`review_notes.md`](review_notes.md)에 적는다.** DB는 값만 가볍게 두고, 리포트와 패키지별 근거(해시 일치, 코드 단서, 리포트의 서술)는 문서로 남겨서 다른 사람이 검증할 수 있게 한다.
- **후보는 `scripts/find_review_candidates.py`가 출력만 한다.** 리포트 설명문에서 탐지 도구가 한계를 인정한 표현이나 작성자의 연구 목적 표방을 찾는다. 정밀도와 재현율이 낮아서 라벨을 자동으로 붙이지 않고, 사람이 걸린 문장을 읽고 판단한다. 검증 결과는 `review_notes.md`에 있다.

## 백업과 공유

`scripts/backup_db.py`는 SQLite의 온라인 백업 API로 DB를 복사한다. 수집 루프가 쓰는 도중에도 커밋된 상태 기준의 일관된 복사본이 만들어지고, 단순 파일 복사처럼 쓰기 중간 상태가 섞일 위험이 없다.

- `backups/index_<날짜시각>.sqlite`는 로컬 스냅샷이고 git에서 제외한다. 분석은 라이브 DB 대신 이 복사본으로 하는 것을 권장한다.
- `dataset/index.sqlite`는 공유용 최신본이고 `--publish`를 줄 때만 갱신된다. 라이브 DB(루트의 `index.sqlite`)와 별개 파일이라서 다른 사용자가 `git pull`해도 각자의 라이브 DB에는 영향이 없다. 파일 하나를 계속 덮어쓰는 방식이라 스냅샷을 커밋마다 쌓는 것보다 저장소가 비대해지지 않는다.
